# 兼容与诊断

本工作流依据 Windows 剪映专业版 **11.6.0.14551** 的本地样本与 `pyJianYingDraft 0.3.0`。字段不是剪映官方稳定 API，其他版本需新样本和小工程验证。

## 已确认的结构问题

| 症状 | 旧输出的问题 | 新工程规则 |
| --- | --- | --- |
| 自由层级开着，文字/图片/视频仍无法放同一排 | 仅开模式，实际仍是 `video` / `text` 专用轨道 | 可视轨道实际为 `mixed` |
| 多个主轨、空主轨难以删除 | 多条可视轨被标 `flag=0` | 唯一有内容的底部主轨为 0，副轨为 2 |
| 整理后层级或镜像不一致 | 索引或镜像未同步 | 写轨道索引并同步主时间线和项目配置 |

主草稿配置：

```json
{"render_index_track_mode_on": true, "mixed_track_mode_on": true, "free_render_index_mode_on": false}
```

`Timelines/project.json.config` 同时设置前两项。不要仅修改剪映全局“新建工程默认开启”。主草稿 ID、项目 ID、主时间线 ID 对应一致；新安装生成新项目 ID。不能按本构建器的单时间线规则重写多时间线工程。

## 点击分割无反应、人物无法美颜

用户先遇到直接素材不能分割/美颜，再加入复合片段作为处理办法；复合片段是应对措施，不是已证实的原始原因。

旧生成素材缺少正常本地导入的一组属性。当前兼容配置为每个素材生成独立 `local_material_id` / `unique_id`，内部 `material_id` 留空；片段来源使用 `segmentsourcenormal`，登记 speed、placeholder、canvas、sound channel、material color、vocal separation 等引用。素材默认结构包括 `stable`、`matting`、`video_algorithm`，以及观察到的 `check_flag=62978047`、两个 beauty mode 字段。

这些字段是**整体兼容配置**，没有证据证明某个单独位就是分割或美颜开关。`is_set_beauty_mode` 不等于已设置美颜效果，也不代表一定能识别人脸。先保留正常原视频和原生变换，避免把人物预烘焙成整屏合成素材。

排障使用同源对照，不能同时换文件、位置、时长和属性后声称只找到一个原因：

- A：原始人物 MP4 + 正常本地属性。
- B：旧透明人物 MOV + 旧属性。
- C：同一个透明 MOV + 正常本地属性。
- D：同一个透明 MOV 放入复合片段。
- E：同帧转普通 MP4 + 正常本地属性。
- F：独立三维透明单元。

分割时选中片段、播放头位于片段内部，分别测试按钮和快捷键；美颜另选真实人物片段测试。先检查锁定、选中状态、是否误选复合片段外壳，再判断属性、编码或人脸识别限制。

## 文件与版本

2026-10-13 的用户工程在改名、删除后恢复这一过程中出现黑画面及字体/效果异常。正常快照有真实绝对路径，故障快照的 47 处媒体引用变为未解析占位符，另有两份字体和一份音频仍引用旧草稿目录；素材本体和时间线仍在。修复副本重新定位这些引用、复制相关处理结果后，用户反馈“成功”。这支持“引用失效”的直接诊断，不能确定是哪一步操作触发，也不能断言剪映内改名必然损坏工程。此前将媒体放在草稿名称对应目录并写入绝对路径的方式存在迁移弱点。后续必须按制作与转换文档确定保存位置并验证改名/迁移。

修复不等于已独立打包所有官方字体和特效缓存；本机存在的缓存路径在另一台电脑未必存在。云端完整性必须通过实际上传下载验证，不能据此恢复记录承诺。

### 改名与云下载的第二轮排查（用户实测通过）

用户随后实测：本地改名后黑屏，未改名的副本同时失效；云端下载后的字形变化。故障副本仍引用原名称目录中的字体、复合片段配置和算法结果，复制出来的素材文件存在并不等于其引用已独立。生成的 28 个视频未出现在本地导入登记表中，也缺少 `local_material_id` 和 `unique_id`；47 处视频引用变成同一个未解析占位符。正常手工导入的对照素材有对应的 `draft_materials[type=0]` 条目，条目 ID 与 `local_material_id` 一致。修正这组登记和引用问题后，隔离工程通过用户复测；没有单字段消融测试，不能将原因归结为一个开关。

云下载样本保留了文字、字号、颜色和官方字体资源 ID，但富文本 `content.styles[].font.path` 仍指向旧工程目录的字库。俊雅体副本与官方缓存字库的 SHA256 相同，因此测试稿将已有官方字体 ID 的内外层路径统一到同一真实字库，没有替换字形。`scripts/material_registry.py` 只在两份字库逐字节一致时做这个修正；不猜字体 ID，不将不同字库静默互换。Noto 本地字库与剪映系统字库哈希不同，继续保留原字库。用户确认完整测试工程云端往返通过；这不是任意本地字体跨设备可用的保证。

v0.2.0 在构建和安装时登记实际使用的本地媒体，包括带本地 `music_id` 但无平台 `resource_id` 的音频，并检查引用与登记表。清单支持显式官方字体资源，构建时核对字库哈希，安装时保持官方引用一致。自动检查范围见 [验证记录](validation.md)。完整隔离测试稿保留全部时间线与文字样式，登记 37 个本地文件，统一 167 处官方字库引用。

用户已确认紧急工作恢复稿可继续剪辑。其后独立测试稿单独登记到首页，其他 52 条首页记录保持不变；2026-10-13 用户完成改名及云端测试后回复“通过了，打包skill”。据此将修复合入正式版本，不改工作稿。这是用户报告的整套验收结果，不是自动点击软件取得的逐项记录。

时间为微秒，按帧端点计算时长。MediaInfo 的毫秒时长允许不超过 1 毫秒舍入误差，不能给短素材伪造长源区间。某些剪映序列化省略 0，读取 `start` 和主轨 `flag` 时按 0 处理。

明文 JSON 读取失败即停止该导入路径，不以旧稿代替新稿。本脚本不解密、不获取运行时授权、不改应用安装目录。若确需读取用户拥有的新版工程，另按已授权本地读取工具及版本能力处理，只写工作区副本。
